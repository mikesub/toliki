This repo is the single home for the user's coding-agent harness: a cloud VPS hosts the dev environments (one clone per repo, see `etc/repos.conf`), and detached `tmux` sessions are started there to run work autonomously. There are **two kinds of session, and they are not the same thing**:

- **Pipeline sessions** (`<repo>-epic-<N>`) — what dispatch launches. The pane runs a plain Node orchestrator (`workflows/epic-run.mjs` or `fix-run.mjs`) which spawns **one short-lived headless agent process per phase** through an engine adapter. No interactive agent session wraps it, so there is no `--remote-control` channel and nothing to type at: watch one with `tmux attach`, or read it afterwards with `capture-pane` — the pane holds the whole phase log and the final `RESULT <json>` line. This is `DOCTRINE.md`'s **No steering** made structural rather than merely discouraged: there is no input channel to nudge, only kill (`stop`).
- **Interactive sessions** (pool names, or any `-m` message) — a normal Claude Code session started with `--remote-control`, which the user connects to from the Desktop app to work with. Unchanged, and the only place Remote Control still applies.

The split is what makes the pipeline **engine-agnostic**: every phase is a process behind `workflows/lib/engine.mjs`, whose adapter contract carries the model and the charter, so a second vendor's CLI plugs in as another adapter and a per-stage `{engine, model}` tuple. Today one adapter exists (`claude -p`), and no pipeline file names it.

Codex is installed on the VM by `provision.sh`, which refuses a green summary until `codex login status` passes, but it is deliberately **not a pipeline engine yet**: no workflow, launch path, cron entry or adapter invokes it. That staged boundary lets the host installation and headless login settle before engine semantics are designed.

It also holds the shared skills, agents, and the pipelines consumed by the project repos (see "Shared skills/agents/pipelines" below), and the host-side scripts: `provision.sh`, `merge-worker.sh`, the `dispatch.sh` daemon that drains the `ready` queue, and `reap.sh`, which frees the slots dispatch spends.

**`DOCTRINE.md` is the layer above this file**: why this harness exists, the principles it's built on, and — with reasons — what was deliberately rejected. Read it before proposing any change to the pipeline's shape, adding a config file, relaxing a gate, or re-opening a settled trade-off; the rejections are written down precisely so they don't get re-litigated.

## Layout

- `etc/repos.conf` — machine-local registry + naming config, **gitignored**; each machine seeds it from the tracked `etc/repos.conf.template` (see below).
- `etc/lib.sh` — the shared helpers (`repo_path`, `full_name`, `slugify`, `sq`, ...) and the single entry point that sources `repos.conf`; every script sources this, and it fails with the copy-the-template instruction when the local conf is missing.
- `bin/dispatch.sh` — host-side queue driver, one tick per cron fire. The primary launch path (see below).
- `remote-control.sh` — laptop-side operator CLI. At the repo root, not `bin/`, deliberately: `bin/` holds only scripts that run ON the VPS, and this is the one script that runs from the laptop (it sshes the rest over).
- `bin/launch.sh` — host-side launch primitive, and the only thing that creates a session. Runs ON the VPS; `remote-control.sh start` calls it over ssh, `dispatch.sh` calls it directly. `--epic N`/`--fix N` create the pipeline's git worktree and run the orchestrator in it; without them it starts an interactive claude, as before.
- `workflows/epic-run.mjs`, `workflows/fix-run.mjs` — the two pipelines, plain Node, no npm dependencies. `workflows/lib/` holds what the harness used to provide: `engine.mjs` (the adapter — how a headless agent process is spawned, and the only file that names a vendor), `runtime.mjs` (`agent`/`parallel`/`phase`/`log`, the concurrency gate, per-step timeouts, signal forwarding), `schema.mjs` (structured-output shape check), `cli.mjs` (argv, the `RESULT` line, exit codes), `status.mjs` (the issue's live status comment — created once, edited in place through `runtime`'s phase/log hooks, best-effort so a GitHub blip never fails a run). Between them the pane answers *what happened*, the status comment answers *is it alive and where*, and the PR answers *what was built*.
- `bin/merge-worker.sh` — host-side merge queue: drains the epic pipeline's finished PRs, one at a time per repo. Runs ON the VPS (see below).
- `bin/merge-autoresolve.sh` + `bin/merge-resolve.awk` — the merge worker's conflict rung: resolves a rebase stop whose every hunk is mechanical, gated by literal line containment (see the merge-worker section). A judgment-class decline exits 4 (the `needs-judgment` marker merge-worker keys on); `--partial` is the fixer session's entry — mechanical hunks settled and staged under the same gate, judgment hunks left marked byte-intact, the rebase left for the caller. Invoked by `merge-worker.sh`, by the fixer pipeline (`workflows/fix-run.mjs`), and by `tests/merge-autoresolve.test.sh`, which covers all of it.
- `bin/merge-tick.sh` — the merge worker's cron shim: fans one worker out per registered repo, concurrently. Exists so `etc/dispatch.cron` never hardcodes the repo list.
- `bin/reap.sh` — host-side sweep that frees what a finished or dead epic leaves behind (the session holding its name, a stale claim ref, a delivered worktree) and flags what it won't touch (orphaned agent processes). Runs ON the VPS (see below).
- `bin/provision.sh` — host-side idempotent rebuild of the whole box. Runs ON the VPS (see below).
- `bin/provision-codex.lib.sh` — the sourced, hermetically testable Codex install and authentication gates used by `provision.sh`; it is not a workflow adapter or launch path.
- `bin/resource-log.sh` — host-side resource sampler, one JSONL line per tick to `~/resource.log`. Read-only observer; starts nothing. Runs ON the VPS (see below).
- `bin/resource-report.sh` — reads that log back (`bin/resource-report.sh [hours]`, default 24). Read-only, safe against a live host.
- `bin/update-claude.sh` — host-side hourly updater for the claude binary: `claude update` to latest, only on an idle box (launch.sh's own count), under dispatch's lock. The one place the CLI moves — `provision.sh` never upgrades a version already present, and a headless `claude -p` never self-updates. Runs ON the VPS (see below).
- `etc/dispatch.cron` — the dispatcher's, reaper's, and merge worker's timers, plus the sampler's and the CLI updater's, installed by hand into `/etc/cron.d/` (deliberately not by `provision.sh`; see below). The first three are one mechanism, all-or-none; the sampler and the updater are not part of that contract.
- `etc/docker-daemon.json` — the Docker build-cache GC policy `provision.sh` installs at `/etc/docker/daemon.json`.
- `etc/harness-logs.logrotate` — monthly rotation for the cron logs (`~/dispatch.log`, `~/reap.log`, `~/merge.log`, `~/update.log`, `~/resource.log`, `~/resource-log.err`), installed by `provision.sh` at `/etc/logrotate.d/harness-logs`. In provisioning rather than a manual step like the cron file, deliberately: installing the cron file turns the box autonomous, whereas rotation changes nothing about how the pipeline behaves — it's host hygiene, the same class as the docker GC policy.
- `skills/`, `agents/`, `workflows/` — the shared harness content; each skill/agent is symlinked **per item** into `~/.claude/{skills,agents}` (real directories, so personal user-level content can coexist).
- `setup.sh` — laptop-side setup: the per-item symlinks, `CLAUDE_HARNESS_DIR`, seeding `etc/repos.conf`. At the root because it runs on the laptop; `bin/provision.sh` does the same wiring on the VM (keep the two in sync).
- `DOCTRINE.md` — premise, goal, principles, and the rejected alternatives with their reasons. The why behind everything else in this repo.

Deploying to the VM = `git pull` in this repo's clone at `/home/ubuntu/toliki` (`HOST_CONTROL_DIR` in `etc/repos.conf`).

## Shared skills/agents/pipelines

`skills/{spec,epic,fix-conflict,commit,bugreport}` and `agents/{architect,coder,reviewer,explorer}.md` are the canonical copies, discovered as user-level via **per-item symlinks** in `~/.claude/skills` and `~/.claude/agents` — real directories, one link per skill/agent, created by `./setup.sh` on the laptop and `provision.sh` on the VM. Per item deliberately: a whole-directory symlink would make this repo the only possible source of user-level content; with real directories, personal skills/agents live alongside the harness set, and both scripts refuse (rather than replace) any same-named entry that isn't a link into this repo, since it would silently shadow the shared copy. The pipelines are **not** skills and are not launched through one on the host: `dispatch.sh` → `launch.sh --epic N` runs `workflows/epic-run.mjs` in the pane directly, and `--fix N` runs `fix-run.mjs`. The `/epic` and `/fix-conflict` skills survive only as the laptop-side manual entry points, and they now do one thing — resolve `$CLAUDE_HARNESS_DIR` (set in each machine's `~/.claude/settings.json` `env`, the only value that differs between laptop and VM) and run the same `node …/workflows/*-run.mjs --issue N` in the background, then report its final `RESULT` line. Nothing about a run depends on which of the two paths started it.

**Which skills a model may invoke on its own is a safety setting, not a preference.** Every user-level skill is visible to every `claude -p` agent a pipeline spawns, and an agent that wanders into one is an autonomous run doing something nobody scripted. So the shared set is invocable only where auto-invocation is the point:

| skill | model-invocable | why |
| --- | --- | --- |
| `spec` | yes | the conversational entry point — you want "let's design X" to reach it |
| `epic`, `fix-conflict` | no | dispatch owns both queues; these are break-glass overrides you type |
| `commit`, `bugreport` | no | both *write* (a push to main, a filed issue) and both are deliberate acts. `/commit`'s "push straight to main" would be actively wrong inside an epic, and a stray `/bugreport` would file issues outside ship's gated follow-up path (two gates, cap of 3) |

`/triage` is exempt from the concern rather than from the rule: it is project-level in this repo, so it never appears in a project checkout where a pipeline agent runs, and its natural-language trigger ("what got stuck?") is exactly how it is meant to be reached.

**The agents are still shared, and still matter.** Each phase spawns its engine process with an `--agent <name>` charter from `agents/`, so `architect` remains read-only (no Write/Edit) and `reviewer` remains a judge that cannot patch what it is judging — the same tool restrictions as before, now applied per process instead of per subagent. A missing or renamed agent file therefore breaks a phase's charter silently: the process still runs, just without its restrictions.

- **Shadowing gotcha:** PROJECT-level skills/agents shadow user-level ones, so a project-local `.claude/skills/<name>` or `.claude/agents/*` with a shared name silently wins over the shared copy. Genuinely project-specific skills (log fetchers and the like) belong in their repos; copies of the shared set do not. toliki's own `/triage` (the operator's sit-down brief) is exactly that class: it lives at `.claude/skills/triage`, project-level in this repo, deliberately not in `skills/` — a user-level link would surface an operator-only skill in every project on the machine.
- The agent registry refreshes lazily (~40 min to notice a file change) while skills refresh in seconds — don't mistake that lag for a broken symlink.
- Each project keeps its own CLAUDE.md and `.claude/rules/`. Nothing project-specific lands here — the epic pipeline discovers the one per-repo fact it needs (the package list) from the repo itself rather than from config, on a one-line contract: a package is a directory whose package.json declares `scripts.verify`. Everything a project wants gated goes *inside* that script, including any real-database tier, which the project triggers from its own path-diffing bash gate — deterministic, no agent in the loop, and covered by CI on manual commits to main as well. Those two files are also the *only* constitution an epic run may amend: `epic-run.mjs`'s triage prompt forbids editing a shared skill/agent/workflow (an autonomous run creating a project-local `.claude/skills/…` copy would silently shadow the shared one) and requires such a rule to be recorded as deferred instead.
- **`verify` runs concurrently, and the worktree is the only thing it owns.** That contract has a functional half (declare `scripts.verify`) and an environmental half, and the second one is easy to miss because nothing announces it: several epics run at once, each in its own worktree, and *other repos* run at the same time on the same box. So anything a verify step touches outside its own worktree — a fixed port, a Docker container or compose project name, a `/tmp` path, a global cache, a shared remote fixture — is contended by an unknown number of concurrent runs. Whatever reaches outside must therefore either **namespace the resource per worktree** or **serialize on a host-wide lock**, and must stay correct when neither is contended (CI runners are isolated, so a lock there is a free no-op — which is exactly why `flock` is the right shape and an "am I in the harness?" branch is not). Most steps need nothing at all: linters, typecheckers and mocked unit tests are worktree-local and parallel-safe by construction, which is why this only ever bites on the tiers that boot something. The live instance is whatif's `backend/scripts/test-db.sh`, which takes a fixed host-wide `flock` before `supabase start` and holds it through the integration run: every worktree of a repo resolves the *same* Supabase containers from the tracked `supabase/config.toml`, so a concurrent `supabase db reset` replays another run's migrations under its tests and hands it a green computed against a schema it never asked for. The lock is keyed host-wide rather than per repo because every repo's `config.toml` binds the *same* fixed ports (54321 api, 54322 db, …), so no two stacks can coexist regardless of project id. **Why this is stated here but implemented there** is `DOCTRINE.md`'s *No shared-resource guards here*: the constraint is universal, the guard is local, and there is no chokepoint to centralize — the harness never invokes `verify`, an agent does, mid-session. Note the practical consequence for documentation: an epic runs with the *project's* CLAUDE.md in context, never this one, so each project restates this rule locally or an agent adding a new tier will never read it.

## Issue tracking

The projects track work as a **flat list of GitHub issues** — no Projects/boards, no milestones, no sub-issues, no parent/tracking issues. One issue is one autonomous, mergeable, independently verifiable change, which is exactly the unit `/epic` consumes: the queue claims an issue and runs it to an open, green PR that `merge-worker.sh` then lands, so anything that isn't a coherent standalone PR is something the pipeline can't deliver. Bug reports are the one parallel track, carried by GitHub's native `Bug` issue type rather than a label.

Ordering lives in GitHub's **`blocked_by` issue dependencies**, deliberately not in labels or a naming convention: a dependency is a real primitive the queue can query — `/epic` skips an issue with open blockers instead of burning a run on it — whereas a label encoding order is inert text nothing enforces, and it goes stale the moment the blocker closes. The label namespace is left entirely to the pipeline's lifecycle, which only automation sets; hand-applied labels would collide with it:

| label | meaning |
| --- | --- |
| `ready` | queued, unclaimed — this is the build queue |
| `in-progress` | a run has claimed it (prepare sets this) |
| `ready-to-merge` | epic finished, PR open, gates cleared → `merge-worker.sh` takes it |
| `ready-to-review` | epic finished, PR open, something was deferred → a human decides |
| `failed` | blocked; needs a human |
| `needs-judgment` | rides beside `failed`: the merge worker declined a judgment-class rebase conflict — this is the fixer queue (see the fix-conflict section); cleared only by the fixer's success |
| `fix-attempted` / `fix-retried` | the fixer's attempt ladder (one retry, then a human); never reset by automation — stripping both is how a human grants another round |
| *(issue closed)* | merged |

That table is the whole namespace — **the follow-up issues ship files carry no label at all.** A follow-up is tied to the issue it came out of by the `Follow-up to #N` line in its body, which GitHub records as a cross-reference on that issue's timeline. GitHub's **"relates to"** relationship is what that link means and is the right home for it, but it entered public preview on 2026-08-07 UI-only — no REST path, no GraphQL mutation, no `gh` subcommand — so an autonomous run has nothing to call; when the API lands, the filing line in `epic-run.mjs`'s ship prompt is the one place to upgrade. The relations that *are* scriptable both say the wrong thing: `blocked_by` would hold the queue back on work nobody is waiting for, and sub-issues are ruled out by the flat-list model. The two success labels are the merge gate's verdict rather than a mood: which one an issue ends up with is computed in `epic-run.mjs` from structured counts, and it decides whether the change merges unattended or waits for a person.

**`skills/spec/ISSUE-TRACKING.md` is authoritative** — this section explains the model, it doesn't define it (the same split the doc already used for labels: the executable artifact is the source of truth, prose points at it). It lives inside the `/spec` skill because `/spec` is its only consumer: `/epic` and `epic-run.mjs` inline what they need in their own prompt text.

## etc/repos.conf

The registry of launchable repos, as ordered `<name>=<path on host>` entries (`myapp=/home/ubuntu/myapp`, ...). The **first entry is the default** when `-r` isn't given, and it's also the head of every dispatch pass. It's a plain array rather than an associative one (`declare -A`) so it stays portable to bash 3.2 and the order is stable for the usage/error text. It also carries the session-name pool, `HOST_CONTROL_DIR`, `SSH_HOST` (how the laptop dials the host), and the optional `GC_UPSTREAM_REPO`/`GC_UPSTREAM_REL` provenance pointer.

**The file is machine-local and gitignored** — the repo tracks `etc/repos.conf.template` (placeholder values, full comments) and `etc/lib.sh`, which holds the shared helpers (`repo_path`, `full_name`, `slugify`, `sq`) and is what every script actually sources: lib.sh sources `repos.conf` beside itself, erroring with the `cp etc/repos.conf.template etc/repos.conf` instruction when it's missing. The split is deliberate: the helpers are *code* (fixes must reach every checkout through git), the registry is *this machine's config* (private repo names stay out of the public repo). Each machine — laptop and VM — keeps its own copy, which survives `git pull`, and that per-checkout sourcing is what keeps naming logic identical on both sides.

`MAX_PARALLEL_EPICS` is the host's slot budget — how many sessions may run at once, enforced in `bin/launch.sh` (why there and not in the dispatcher is above). It counts every running session whoever started it, an interactive one included — that's load like any other. It's sized against the box rather than the queue: the orchestrator's own concurrency gate is `min(16, cores-2)` agent processes (`EPIC_MAX_PARALLEL_AGENTS` overrides it), so each pipeline session is one cheap node process plus up to that many agents (on 6 vCPU, `2` sessions is ~10 processes at full tilt). Start it low — an under-full box only drains slower, whereas contention is expensive to tell apart from a pipeline bug. This is the one number that decides how hard the host gets pushed; raise it after watching a full drain, not before — which is what `bin/resource-log.sh` exists to make possible (`bin/resource-report.sh 24` is the evidence, see below).

`REPO_ORIGINS` is a **parallel** array of `<name>=<owner/repo>` read by `provision.sh` (to clone) and `merge-worker.sh` (to pass `gh -R`, so every API call names its repo instead of depending on a cwd); launch.sh works from paths that already exist and doesn't need it. It's separate rather than a third field in `REPOS` so the `<name>=<path>` parsing in `repo_path()` and every existing caller stays untouched. GitHub slugs rather than URLs because provisioning clones with `gh repo clone`, which carries the host's gh credentials — the repos can be private and span several owners, so there's no URL shape to derive a slug from.

- **Adding a repo takes three steps**, all required: (1) add a `<name>=<path>` line to `REPOS` **and** a `<name>=<owner/repo>` line to `REPO_ORIGINS` — in the *host's* `etc/repos.conf` (and the laptop's, so `-r` validation matches; the file is local, there's nothing to commit), (2) re-run `bin/provision.sh` on the host, which clones whatever the registry lists and doesn't have yet, and (3) **`ssh` in and run `claude` once in the clone to accept the workspace-trust dialog.** This one now bites only **interactive** sessions — `--worktree` refuses to create a worktree in an untrusted directory (`Error creating worktree: Workspace trust not yet accepted`), so `claude` exits instantly while `start` still looks like it worked, and the session shows up as `dead (at bash prompt)` in `ls`. Pipeline sessions escape it from both ends: launch.sh creates their worktree with plain `git`, and a headless `claude -p` skips the trust dialog outright. Do step 3 anyway — an untrusted clone is a trap waiting for the first person who opens a session there. Trust is per-directory and interactive (it needs a TTY, so it can't be done from the detached session itself); once accepted it's recorded in `~/.claude.json` as `projects["<path>"].hasTrustDialogAccepted` and never needs repeating. Note `--dangerously-skip-permissions` does **not** cover this. If a session dies this way, fix the trust and then `restart` it — a plain `start` would just report "already running" against the dead session.
- **The trust trap has a global sibling: bypass-permissions acceptance**, and it's nastier because it deadlocks *silently*. The first time `--dangerously-skip-permissions` is ever used on a host, claude stops at the "Bypass Permissions mode" consent dialog. Whether that can still hang a *pipeline* run is unverified — the flag is passed to every headless agent process, and a `-p` run has no TTY to draw a dialog on, so it should fail loudly rather than wait; treat it as an open question until a fresh host proves it, and accept the dialog on any new box regardless. For an interactive session it hangs exactly as it always did. `ls` reports it `running (claude)` because claude *is* the foreground process, so the failure looks like a healthy session doing nothing; `reap.sh` can't catch it either, since the issue never reaches `in-progress` and no terminal label ever appears. (`capture-pane` shows the dialog, same diagnostic as the dead-session traps.) Unlike trust it's per-host, not per-directory: accept it once — run `claude --dangerously-skip-permissions` interactively, accept, exit — and it's recorded as `skipDangerousModePermissionPrompt: true` in `~/.claude/settings.json`, never asked again. `provision.sh` checks it alongside the other interactive gates but never sets it: it's a consent decision, same class as the logins and trust.

## dispatch.sh (driver), remote-control.sh (operator interface), launch.sh (primitive)

Three entry points, one mechanism: **`bin/launch.sh` is the only thing that creates a session**, and every caller goes through it. `bin/dispatch.sh` is how epics normally start; `remote-control.sh` is how the human inspects and overrides the result.

**bin/dispatch.sh** (host-side, one tick per cron fire) is the primary launch path. It walks each repo's `ready` queue oldest-first — the same `gh` query as the `/epic` skill's queue walk — and calls `launch.sh --epic <N>` for each unblocked issue until the host is full.

Before the `ready` walk it drains a second queue: **`needs-judgment`** (issues whose PR the merge worker declined on a judgment-class rebase conflict — see the fix-conflict section), calling `launch.sh --fix <N>` through the same primitive, which names the session `<repo>-epic-<N>` like any epic. Fixers go first deliberately — each is a finished epic one resolved conflict away from a reviewable PR, and the walk is bounded (at most one fixer per repo per tick, and none while any candidate in the repo still has a session — fixers are serial per repo because each rebases onto the same moving `main`), so it cannot starve the `ready` queue. Two of its choices look odd until the reaper is in the picture: the query excludes `fix-retried` (an exhausted attempt ladder waits for a human, not for the next tick), and **the launch itself swaps `failed` → `in-progress` before creating the session**. That swap is not a claim — the tmux session name is the claim, same as the ready walk's already-has-a-session check — it is a shield: `failed` is terminal for `reap.sh`'s sweep, and a fixer necessarily launches more than `TERMINAL_SETTLE_MINUTES` after that label's last write (its predecessor session had to settle and be reaped first, with nothing touching the issue in between), so a session launched onto a still-`failed` issue would be killed by the next sweep — a minute out — long before its own prepare could swap the label. Swapping synchronously in the tick is the only ordering that closes the window; a launch that then fails reverts the swap so the issue drops back into the queue. Two guards keep the swap honest: the walk probes `launch.sh --check-capacity` first, so a full host ends the tick with zero label writes instead of a swap-revert pair per minute for as long as the drain runs (the probe is launch.sh's own `capacity_gate`, so the counting still lives in exactly one place); and after the swap it re-reads the issue directly — the queue rode gh's search index, which lags label edits by up to a minute, so a human takeover (stripping `needs-judgment`) could otherwise race the tick and end up with its `failed` label silently eaten and an unreapable fixer session on an issue that is no longer the fixer's. If the strong read disagrees, the swap reverts and the walk moves on.

It runs `gh` *inside* the clone, resolving the GitHub repo from that checkout's own origin, and so never reads `REPO_ORIGINS` — the opposite of `merge-worker.sh`, which names its repo explicitly with `gh -R`. The difference is deliberate: dispatch's whole job is to pair "issues from repo X" with "a session in clone X", so taking both from the same place makes a registry entry that disagrees with the clone unable to launch a session against another repo's queue. The worker has no such pairing to keep — it acts on PR numbers — so explicit is better there.

- **It launches; it never claims.** The claim is a unique commit the pipeline's own prepare phase pushes to `epic/<N>-<slug>`, and a dispatcher that pre-created that ref would make every run it launched refuse its own claim as another run's. Two ticks racing on one issue is therefore safe by construction: one wins the ref, the loser skips in seconds — far cheaper than the coordination it would take to never over-dispatch.
- **Fail closed on the blocker check.** A `blocked_by` query that errors counts as *blocked*, never as clear — "couldn't check" must not dispatch a run the queue was deliberately holding back. A repo whose queue query fails is passed over whole; the other repos still get their tick.
- **An issue that already has a session is skipped.** It stays `ready` until prepare swaps the label, so for the first minutes of a run it is still a queue candidate — without the check the next tick spends itself re-offering an issue that is already building.
- **Terminal labels are excluded from the search** (`-label:ready-to-merge -label:ready-to-review`): prepare's `ready` → `in-progress` swap is best-effort, so a stale `ready` can survive beside a terminal label — and searched by `ready` alone, that finished issue would be re-picked every tick, each launch a wasted spawn exiting via the already-claimed guard while the logs look healthy. An epic that ends at `ready-to-review` never closes its issue, so without the exclusion that loop wouldn't even self-heal on merge.
- **Repos interleave one issue per pass** rather than draining in `REPOS` order. Since `REPOS[0]` is also the default repo, order-draining would starve the others in the *likely* case, not the unlucky one.
- **Ticks can't overlap** (`flock`; a tick that finds it held exits quietly — the next one is five minutes out and the queue is still there). Two ticks reading capacity at the same instant would each see the same free slots and both fill them, which launch.sh's own count cannot catch because both pass it before either creates a session.
- **Exit status is the tick's health**: `0` clean — including "nothing ready" and "hit capacity" — and `1` if any launch failed. A launch.sh *config* rejection aborts the tick rather than repeating identically down the queue: twenty copies of one error ending in a normal-looking summary is exactly what a broken cron job looks like to nobody reading it.
- `-n/--dry-run` reports without launching (capacity is not simulated, since asking costs a launch); `-r <repo>` restricts the tick to one repo.

**etc/dispatch.cron** carries all three timers — dispatch, reap and the merge tick, each on `* * * * *` — installed by hand:

```bash
sudo install -m 0644 /home/ubuntu/toliki/etc/dispatch.cron /etc/cron.d/harness-dispatch
```

**Install all three lines or none** — they are one mechanism. Dispatching without reaping fills the box and stops: a finished run's session keeps its name, and dispatch skips any issue that still has one — so the queue stalls behind sessions nothing will ever relaunch. Reaping without dispatching frees slots nothing then claims. Dispatching without the merge tick stalls the last mile: every clean epic parks at `ready-to-merge` with an open PR nothing lands. **provision.sh deliberately does not install the file** — turning the box autonomous is a deliberate act, not a side effect of provisioning it. A tick is deliberately far shorter than an epic takes — an idle one costs a single `gh` call per repo and exits in a second or two — so a freed slot refills quickly. All three run at the same one-minute period rather than staggered, because they are links in one chain and the slowest sets the pace: dispatch cannot use a slot reap has not freed, and an issue `blocked_by` another cannot launch until the merge worker lands that blocker's PR and closes it. The offsets the file used to carry bought log separation the per-file logs already give, and the collision they avoided now self-corrects in a minute instead of five (worst case: dispatch counts a session reap is about to kill, reads the host as full, and skips one launch). The `PATH=` line in that file is load-bearing: cron gives a job `/usr/bin:/bin`, which has no `claude` (it lives in `~/.local/bin`), and the failure is indirect — the session starts, the pane can't find its command, and `ls` reports `dead (at bash prompt)`, the same symptom as the workspace-trust trap from a completely unrelated cause. It now has to carry **both** `node` (the pane's own process) and `claude` (every agent the orchestrator spawns, resolved through the same inherited PATH); the adapter turns a missing `claude` into a message naming this line, because mid-run it would otherwise read as a phase that produced nothing.

**The slot cap lives in launch.sh, not in dispatch.sh.** `MAX_PARALLEL_EPICS` is enforced at the one place that actually creates sessions, because that is the only place every caller passes through. Counted in the dispatcher it would bound *the dispatcher*, and every manual `./remote-control.sh epic N` would walk straight past it — so the two callers together could overrun the box while each believed it was under the cap. It counts **running** sessions (a pane at a shell prompt holds its name but no load), and it is checked **after** the already-exists branch, so merely reporting on a live session is never refused for capacity. A missing or non-numeric value is a hard error, never an implied "no limit" — a cap that evaporates when its config goes missing leaves the box unprotected by the very thing you believe is protecting it. Refusal is exit **3**, distinct from usage/config `1`; that distinction is what lets dispatch read "host is full" as *end the tick* rather than as a failure. `--check-capacity` exposes the same gate as a read-only probe (same `capacity_gate` function, exit 0/3, starts nothing) — dispatch's fixer walk asks it before the label swap a full host would force it to revert, so probing and enforcing stay one piece of code. `--check-idle` is the same count against zero (exit 0 idle, 3 otherwise) — `update-claude.sh` asks it before moving the claude binary, so "busy" is decided by one function.

**remote-control.sh** is the operator interface, not the launch path: `./remote-control.sh [start|stop|rm|restart|ls|stop-all|epic] [session-name...] [-m <message>] [-r <repo>]` (bare `./remote-control.sh <name>` is shorthand for `start <name>`; with no args it prints usage and does nothing). SSHes to `SSH_HOST` from `etc/repos.conf` (an alias resolvable via the local ssh config). `start` is a thin ssh call — it validates the repo and forwards `[name] -m -r` (each arg `sq`-quoted, since ssh mashes the remote command into one shell-parsed string) to `bin/launch.sh`, which owns everything below. `stop`/`stop-all`/`ls` are inline ssh+tmux heredocs; `restart` is stop then start, forwarding `-m` and the resolved repo. Note that `start` and `epic` are subject to the same cap as dispatch — deliberately, per above — so a manual launch against a full host exits 3 with launch.sh's message relayed over ssh.

**bin/launch.sh** (host-side, no ssh anywhere in it):
- **Naming.** Sessions are always named `<repo>-<short>` (`myapp-epic-63`): tmux session names are global to the host but issue numbers are per-repo, and a collision would be *silent* (an existing session makes launch report "already running" and do nothing). Resolution is **idempotent** — an already-prefixed name passes through untouched, so short (`epic-63`) and full (`myapp-epic-63`, as `ls` prints it) forms are interchangeable everywhere; note an explicit short name that happens to begin with a registered repo name is read as a full name. With no explicit name: a `-m` message names the session (slugified: lowercased, runs of non-`[a-z0-9]` collapsed to `-`, trimmed, capped at 40 chars — `-m "/epic #42"` → `myapp-epic-42`); with no usable message it auto-picks the first free pool name from `NAMES` in repos.conf, checked per-repo against the prefixed name (a name is taken if any tmux session by it exists, running or dead; all taken ⇒ error). Explicit name always wins; a derived name that already exists reports running/dead rather than relaunching.
- **Launch.** If the session doesn't exist: `git pull --rebase` in the repo's path (always checked out on `main`, so a new worktree starts from a fresh HEAD), create the detached tmux session, tag it with `tmux set-option @repo <repo>` (so `ls` can report the repo no matter where the pane's cwd sits), then type the command into the pane via send-keys. send-keys-into-a-shell rather than tmux's command argument is deliberate: the pane survives the process exiting, so `ls` shows it `dead` and capture-pane can still read the scrollback — which for a pipeline run is its whole phase log and final `RESULT` line. If the session exists, it reports running vs dead and changes nothing (and doesn't pull).
- **`--epic <N>` / `--fix <N>`: the pipeline path.** The session is named `<repo>-epic-<N>` (no message, no explicit name — both are refused, because every other part of the harness keys on that shape), and **launch.sh owns the worktree**: `${EPIC_WORKTREE_ROOT:-$HOME/.epic-worktrees}/<repo>/<session>`, created `--detach` from the clone's HEAD, following `merge-worker.sh`'s `~/.merge-worker/<repo>` precedent. Detached deliberately: prepare decides which branch to be on, and a worktree already holding `epic/<N>-*` is exactly what its resume guard reads as a live competitor. An existing worktree is **reused** (a resumed epic, a retried fixer) after a scrub — `rebase --abort`, `merge --abort`, `reset --hard`, `clean -fd`. That `clean` has **no `-x`**, which is load-bearing: `-x` would delete `node_modules` (an `npm ci` per relaunch) and `.epics/<slug>/`, whose `epic.md` the resume path appends to. Committed work is never touched — that is what the checkpoints are for. The pane then runs `node <harness>/workflows/{epic,fix}-run.mjs --issue N --session <name>`.
- **Without those flags it starts an interactive claude**, exactly as before: `claude --remote-control $SESSION --dangerously-skip-permissions --worktree $SESSION ['<message>']`, session name == worktree name a deliberate invariant, and Remote Control available for the user to attach to.
- **`-m` / `--message`** seeds an initial prompt as claude's **positional** arg — deliberately not `-p`, which is print/non-interactive mode and would run the prompt then exit, tearing the detached session down. `-m` only applies to start/restart; it doubles as the session name as above. launch.sh runs on the host, so the message is `sq`-quoted once for the pane's shell.

Command notes:
- `epic <ref>`: forwards `--epic <ref>` to launch.sh. Strips one leading `#` from the ref (no doubling); exactly one ref; can't combine with `-m`. **This is the override, not the driver** — `dispatch.sh` launches epics from the `ready` queue on its own; reach for this to jump the queue or to re-run a specific issue. It produces exactly the session `dispatch.sh` would have, which is what makes the dispatcher's already-has-a-session check see a manual launch too.
- `fix <ref>`: forwards `--fix <ref>` — the same override for the fixer walk (see the fix-conflict section). Same ref rules as `epic`.
- `stop` (alias `rm`): one or more names, resolved independently (short forms get `-r`/default repo's prefix), killed in a single ssh call with per-session killed/didn't-exist reporting.
- `stop-all`: kills **every** tmux session on the host (all repos, even hand-made ones). A separate command rather than `stop all` so it can't be confused with a session literally named `all`.
- `restart`: when `-r` isn't given, derives the repo from the session name's prefix, falling back to the default for unprefixed names; forwards it to the fresh start. It **refuses on a `<repo>-epic-<N>` session** (without `-m`): the name says which issue but not whether it was an epic or a fixer, and relaunching one as an interactive claude would leave a live session sitting in the pipeline's worktree with nothing driving it. Stop it and use `epic N` / `fix N`, or just stop it and let the next dispatch tick relaunch it.
- `ls`: all sessions with repo (`-` for hand-made sessions, which carry no tag) and running/dead status.

Note: Archiving/deleting a session from the Desktop app is client-side only — it does not stop the remote `tmux` process. Use `stop`/`restart` to actually tear one down. (It only ever applied to interactive sessions; pipeline sessions never appear there.)

## merge-worker.sh (the last mile)

`bin/merge-worker.sh -r <repo>` runs **ON the host** from cron — its timer is the `bin/merge-tick.sh` line in `etc/dispatch.cron`, which fans one worker out per registered repo — and owns squash-merge order. The epic pipeline itself never merges: a run ends at an open PR and labels its issue `ready-to-merge` (gates cleared) or `ready-to-review` (a human decides); the worker drains the former. A separate worker is what stops a finished epic from holding a build slot while it waits its turn to merge — `DOCTRINE.md`'s "design out the drudgery".

- **One PR at a time, and that is forced rather than conservative.** Merging moves the repo's `main`, and every other queued PR was branched from `origin/main` with its CI computed against the commit that used to be there. So each merge invalidates the next PR's green: the worker rebases onto current main, re-pushes, waits for the checks to re-run **on the rebased head**, and only then merges. Merging on the pre-rebase green would assert a check that never ran against what is actually landing — the lying gate `DOCTRINE.md` is built to refuse. Two workers on one repo would each do exactly that to the other's PR, so there is no parallelism being given up here.
- **Serial per repo, not host-wide.** Repos have independent `main`s, so one repo's merge invalidates nothing in another. Each repo gets its own invocation and its own `flock`; concurrency across repos is free and is taken.
- **It never exercises judgment, and the one thing it fixes is proved rather than guessed.** A rebase conflict whose *every* hunk is mechanical is resolved in place by `bin/merge-autoresolve.sh` (the git half) and `bin/merge-resolve.awk` (the text half): a hunk is mechanical when its diff3 base section is empty — both sides added different content at the same point, so the resolution is both sides' lines — or when exactly one side reproduces the base verbatim and merely added around it, so the other side's edit of those base lines wins and the additions stay put. The empty-base rule carries one exception, learned the hard way on 2026-08-17: it settles which *lines* survive but not how they *nest*, and concatenation decides that silently — so when the second block opens at a deeper indent than the first, it lands as a child of whatever the first block ended with rather than beside it, a placement neither author wrote. Containment is blind to it (every line is present, once), which is exactly why the resolver declines that shape to judgment instead. Two gates make this a merge strategy rather than a repair: a literal line-containment check that every line of both sides survived into the resolution (the class where picking a side silently deletes the other side's test block and `verify` stays green — the check the test suite is blind to), and CI re-running on the rebased head exactly as for any conflict-free rebase. No model, no session, no dispatch slot; a single hunk where both sides touched the same base lines declines the whole PR to the paragraph below, and the resolution is recorded as an issue comment naming files, hunks and classes, so the audit trail lives on GitHub rather than in `~/merge.log`.
- **Beyond that one rung it never fixes anything.** A judgment conflict, a red check, a timed-out CI (~30 min cap) or a failed merge leaves the PR open, flips the issue to `failed`, comments which (a declined conflict names the file and hunk), and moves to the next PR. The judgment class is marked, not just failed: `merge-autoresolve.sh` exits 4 for exactly that class, and the worker adds `needs-judgment` beside `failed` — the queue dispatch's fixer walk drains (see the fix-conflict section), so the queue is a label query rather than a grep of comment prose. Every other decline stays plain `failed` for a human. Infrastructure failures are the deliberate exception — a failed `git fetch` or `gh` call aborts the whole run instead, because a network hiccup must never write `failed` onto an issue whose PR is fine. Queries can abort unconditionally (a query that errored carries no verdict), but the **merge call cannot**: a merge GitHub genuinely refuses *is* that PR's verdict, and exit status alone can't tell it from an outage. So the merge and the read-back that confirms it classify the error text (`transient_gh_error`) and abort only on an infrastructure signature — deliberately generous, because the two mistakes aren't symmetric: a misread refusal costs one wasted tick, a misread outage writes `failed` onto a healthy PR and takes a human to undo. That is not hypothetical — during the 2026-08-17 GitHub incident a 503 on `gh pr merge` failed a perfectly mergeable PR, and only a *second* 503 on the relabel kept the verdict from sticking.
- **It merges in a dedicated worktree** (`~/.merge-worker/<repo>`), never in the repo's clone: launch.sh assumes that clone sits on `main`, and a rebase would park it on a detached epic head — surfacing much later as a session that built from the wrong base.
- A PR already sitting on current main is merged on its **existing** checks: the rebase is a no-op, so those checks were computed against this exact base, and re-pushing an identical sha would trigger no new run to wait for.

## fix-conflict (the judgment rung above the merge worker)

The deterministic rung settles hunks that need no judgment; what it declines as judgment-class — both sides edited the same base lines, both kept the base and added around it, or an ambiguous placement — goes to a **fixer session**: `DOCTRINE.md`'s "crons watch, models act", with the cheap awk classifier as the watcher and one model session as the actor. The pieces: `merge-worker.sh` labels the issue `failed` + `needs-judgment` (exit 4 from `merge-autoresolve.sh` is the trigger), dispatch's fixer walk launches it with `launch.sh --fix N` (no skill in the loop — the merge worker only *labels*; it never runs the fixer itself), and `workflows/fix-run.mjs` runs the pipeline: rebase the PR onto `origin/main` in the session's own worktree (detached at the PR head — no branch checkout, so a leftover epic worktree holding the branch can't collide), re-settle the mechanical hunks with `merge-autoresolve.sh --partial` (same containment gate, so the mechanical share is never re-litigated by the model), have the model resolve **only** the hunks left marked — fed both sides' diffs and both sides' issue bodies, required to state what each side intended and show both surviving, told to **escalate instead of guessing** — then `npm run verify` in every discovered package (a red verify fails the run; the fixer never fixes code), then a blind adversarial agent tries to refute "both intents survived" (refute-by-default; the resolver's stated intents are withheld from it), and only then `git push --force-with-lease` and the audit comment naming every hunk, both intents, and the gates that ran.

- **It lands `ready-to-review`, never `ready-to-merge`.** Whether the PR could merge unattended was decided before the conflict existed; a rewritten resolution resets that to "a human glances". Promotion stays the human's, and the merge worker re-runs CI on the true base after it — so even a wrong resolution cannot reach `main` unreviewed. The push is the LAST step, after verify and the adversarial check: a refuted resolution never touches origin, and a blocked or killed fixer leaves the PR branch exactly as it found it.
- **The attempt ladder is labels, and it is verified, not best-effort.** Prepare adds `fix-attempted` on the first run, adds `fix-retried` (and proceeds) when `fix-attempted` is already present, and refuses outright when `fix-retried` is present — one retry, then a human. The write is confirmed by reading the labels back, because it is the bound that keeps the loop finite: dispatch excludes `fix-retried` from the queue, so an exhausted issue stops being launched at all. The ladder deliberately never resets — not on success, and not when a later `ready-to-review` → `ready-to-merge` promotion re-conflicts (a human sits inside every such cycle); stripping the two `fix-*` labels is how that human grants another round. To take an issue away from the fixer entirely (hand-resolving instead), strip `needs-judgment`.
- **Sessions are `<repo>-epic-<N>` on purpose — do not invent a second name pattern.** Reap's terminal sweep covers fixers untouched (`ready-to-review` and `failed` are terminal for a session either way), dispatch's has-session checks guard both walks by the same mechanism, `MAX_PARALLEL_EPICS` counts fixers like any session, and a full host defers a fixer (launch exit 3 ends the tick, the label swap reverts) rather than failing it. The one wrinkle the name reuse buys is the reap race at launch, which is why dispatch — not the session — swaps `failed` → `in-progress` (see the dispatch section).
- **A fixer that dies mid-run self-heals bounded by the ladder.** Its issue sits `in-progress` + `needs-judgment`: a dead pane parks the repo's fixer walk (the session still exists) and reap flags it for a human, exactly like a dead epic; a *vanished* session (operator `stop`, dispatch crash between swap and launch) is simply relaunched next tick, and the relaunch consumes the retry. Workers stay disposable.
- **Genuine contradictions still go to a human.** The resolver escalates (`failed`, with the file/hunk and why the intents cannot both survive) rather than picking a side — measured on the live declines this class is rare, but the path exists. Same landing for a red verify, a refuted check, or a push the lease rejected.
- Manual override: `./remote-control.sh fix N` — it produces exactly the session dispatch would have (explicit `epic-N` name; a message-derived name would be `fix-conflict-N`, which nothing reaps and nothing checks). A manual launch skips dispatch's label swap; prepare re-does it, but a sweep can kill the session in that first minute if the issue has sat `failed` a while — harmless, dispatch relaunches it within a tick.

## reap.sh (freeing what a finished run leaves behind)

`bin/reap.sh [-n|--dry-run]` runs **ON the host** from cron — one sweep, then exit; no ssh, no launching, never touches a repo's working tree. It is what makes `MAX_PARALLEL_EPICS` a rotating budget instead of a one-time allowance, and it exists for two leaks that nothing else closes, neither of which is visible from reading the code that causes them:

- **A finished epic leaves its session behind.** The orchestrator process does exit when the pipeline ends, so the *slot* frees itself — that is new; the interactive sessions this replaced sat at a prompt holding a slot forever. What does not free itself is the session **name**, and that is what dispatch's has-session checks read: until the session is gone, that issue cannot be dispatched again. A run that ended in a skip or a blocker is exactly the one that needs relaunching, so without the sweep the queue stalls on issues nothing will re-offer.
- **A run that dies mid-claim strands its issue.** `epic-run.mjs` prepare **claims (4c) before it labels (5a)** — the ref push is the lock, the `ready` → `in-progress` swap is only reporting. Die in between and the issue keeps `ready` with a claim ref on origin: it stays the *oldest* candidate, so dispatch offers it first every tick, every run refuses it at 4b/4c as "claimed by another run", and **nothing reports it** — no `failed`, no comment, while work keeps flowing behind it and the drain looks healthy.

The contract, in three independent passes plus one thing it only reports:

1. **Sessions.** Only `<repo>-epic-<N>` sessions are ever candidates — pool-named and hand-made sessions are the user's own work and are never touched. A terminal issue, settled for `TERMINAL_SETTLE_MINUTES` (default 5), ⇒ kill the session. A session whose process exited at a shell prompt while its issue is **not** terminal is reported and **left alive**: `capture-pane` is the only place the reason still exists, and killing it would destroy the one record of why. That costs no capacity — a pane at a shell prompt holds its name but doesn't count against the cap. Note the pane's last line settles which of the two it is: a run that finished normally prints `RESULT <json>`, and one that died mid-phase prints nothing.
2. **Stale claim refs.** For each `epic/<N>-*` ref on origin whose tip is still the claim commit, with no live session on that issue and older than `CLAIM_GRACE_HOURS` (default 6): delete it, which puts the issue back in the queue.
3. **Delivered worktrees.** launch.sh creates one per run and only ever removes one to replace it, so without this every issue the box has built keeps a checkout and its `node_modules` forever (`git worktree prune` does the opposite job — it clears entries for directories already gone). A worktree is removed when its issue has **no `epic/<N>-*` ref on origin at all**, no tmux session of its own exists, and it is older than `WORKTREE_GRACE_HOURS` (default 24). The first condition is the safety proof and it rests on the same fact as pass 2: prepare pushes its claim ref *before* doing any work and Ship force-pushes to that same ref, so no ref on origin means no work exists that anyone could want — the PR merged and GitHub deleted the branch, or the run died before it wrote anything. A repo whose ref listing failed is skipped entirely rather than read as "no refs". **That proof depends on the repo deleting merged branches** (Settings → General → "Automatically delete head branches"): with it off, the ref outlives the merge forever, so nothing is ever collected and every issue the box builds leaves a checkout and its `node_modules` behind. It fails safe — nothing is wrongly deleted — which is why the leak is invisible until a disk fills, so `provision.sh` reports any repo that has it off.

And one it deliberately only reports: **agent processes orphaned by a SIGKILLed run**. Each phase runs in its own process group so a timeout can take an `npm run verify` tree with it, and the orchestrator forwards signals so a normal `stop` sweeps them — but its own SIGKILL or the OOM killer cannot be forwarded, leaving agents alive under no session. They are invisible to `MAX_PARALLEL_EPICS` (which counts tmux panes, not processes), so the box can sit loaded past its budget while the harness reads it as idle. Reap warns (non-zero exit) and leaves them: a long verify tier and a hung one look identical from outside, and unlike everything else it kills, an orphan is proved finished by neither a label nor a commit. `/triage` surfaces the same thing with the command to clear it.

Five things that are decisions, not details:

- **Terminal is the label, and the issue closing is only a backstop.** The lifecycle table is in "Issue tracking" above; what matters here is that a run ends at an *open* PR, so `ready-to-merge`, `ready-to-review` and `failed` are each terminal **for the session** while the issue stays open for as long as `merge-worker.sh` takes to land it. Waiting for closed would hold a slot across the entire merge queue, and `ready-to-merge` is the gate-clear path — miss it and every clean epic leaks a slot. A closed issue is still accepted, for the run whose PR merged before the sweep noticed.
- **A terminal label has to settle before the kill.** Ship applies `ready-to-review` and a *separate* step promotes it to `ready-to-merge` — and that promotion runs inside the session. Killing on sight would sometimes land in that window and leave a clean run parked at `ready-to-review`, waiting on a human who has nothing to decide. Reap requires the issue to have been untouched for `TERMINAL_SETTLE_MINUTES` first; nothing edits the issue between the run ending and the merge worker picking it up, so the window is real and cheap. A **closed** issue skips the settle wait entirely: closed means the PR merged, and the clock the window reads is reset by the merge worker's own writes (the label drop, the `Closes #N` close) — waiting on it would only delay cleanup of work that is already delivered.
- **The claim ref stays claim-tipped for the whole run**, not for an instant: the code and triage phases checkpoint *locally* and only Ship pushes, so nothing lands on top of the claim until the epic is nearly over. That is why staleness can't be a short timeout — the live-session check is the real guard and the grace is only a backstop for a run whose session isn't named `<repo>-epic-<N>` (a hand-written `-m`).
- **Liveness is read from tmux, before the GitHub query.** Whether a run is alive is local knowledge; deriving it after the issue lookup would let a GitHub outage strip a live run's claim of its guard and delete a ref out from under it.
- **The tip alone proves the ref holds no work**, which is what makes deletion safe rather than destructive: the claim commit is pushed first and any real work lands on top of it. Everything reap could not check — a failed `gh` query, a ref it could not fetch — is left alone and reported, and exit is non-zero whenever something needs a human (a flagged session, a check that could not be made).

Its timer ships in `etc/dispatch.cron` next to the dispatcher's and on the same one-minute period, because the two are only useful as a pair: dispatching without reaping fills the box and stops, and reaping without dispatching frees slots nothing claims. Matching periods matter once the box is at `MAX_PARALLEL_EPICS` — a slower sweep would make the reaper, not the dispatcher, the thing setting how fast the queue drains. What it can't shorten is `TERMINAL_SETTLE_MINUTES`: a session is still unkillable until its issue has been terminal and untouched for that long, so the faster sweep only trims the wait *after* that window, never the window itself. Run `-n` first if you want to see what a sweep would do; it's the safe way to inspect a host without changing it.

## resource-log.sh / resource-report.sh (the evidence for the slot budget)

`bin/resource-log.sh` samples the box once a minute from cron into `~/resource.log` (JSONL); `bin/resource-report.sh [hours]` reads it back. Both are **read-only observers** — they start nothing, kill nothing and touch no pipeline state, so unlike every other script here they're safe to run against a live host on your own initiative.

They exist because `MAX_PARALLEL_EPICS` can only be raised honestly by watching a real drain, and the failures that set the ceiling are *conditional*: the real-DB tier booting a Supabase stack under an already-loaded box, or several epics hitting their review fan-out at the same moment. Both are minutes long, neither announces itself, and a snapshot taken by hand afterwards cannot see either.

- **Counters, not averages — this is the load-bearing design choice.** PSI exposes a cumulative `total=` in microseconds of stall and `/proc/stat` exposes cumulative jiffies, so the delta between two consecutive samples is the *exact* stall and *exact* utilization for that window regardless of sample rate. That is why one sample a minute loses nothing: a 20-second burst between ticks is fully accounted for, it just can't be placed within its minute. Sampling `avg10` instead would alias and would miss precisely the short spikes worth catching. The sampler records raw counters and the report owns every rate.
- **Only stable windows are attributed to a concurrency level.** A window in which an epic started or finished describes neither level, so charging it to the count at either end would understate one and overstate the other. The report accounts for those separately rather than smoothing them in — this is the table the slot budget gets raised on.
- **Gaps and reboots are dropped, never smoothed.** A missed tick or a counter reset invalidates that pair; dropped time is reported, because a summary that quietly covers 3 of 24 hours reads exactly like a quiet 24 hours.
- **Phase detection is zero-touch**, inferred from process names rather than emitted by the projects. Keeping harness-shaped logging out of project repos is worth the two costs, which are named in the script header: a tier shorter than the sample gap can slip through, and lock-wait time is invisible.
- **A session is found by a marker in its argv**, and there are two: a pipeline run is the node orchestrator carrying `--session <name>` (matched only on lines that also name `workflows/*-run.mjs`, so an unrelated `--session` can't invent an epic), an interactive one is claude carrying `--remote-control <name>`. The agent processes an orchestrator spawns carry neither, so they never count as sessions of their own. Their CPU still reaches the right epic, but only **after they exit**: `pid_cpu_jiffies` sums `cutime`/`cstime` alongside the process's own, so a live spike shows in the host-wide totals before it shows per-session.
- Its cron line writes stdout/stderr to a **separate** `~/resource-log.err`, since a stray warning landing in `~/resource.log` would make the report choke on a line that isn't JSON.

## update-claude.sh (keeping the CLI current)

`bin/update-claude.sh [-n]` runs **ON the host** hourly from cron (its line is in `etc/dispatch.cron`, hygiene class like the sampler — not part of the all-or-none contract). It runs `claude update` to the latest release, and only when nothing is running. It exists because nothing else does it: a headless `claude -p` never self-updates (the auto-updater is an interactive-session feature), and `provision.sh` deliberately never upgrades a version already present. Measured on 2026-09-02: the host had sat on 2.1.233 since 2026-08-14 across daily pipeline runs while 25 releases shipped.

Why it matters more than hygiene: the pipelines' tier tables (`MECHANICAL`/`DESIGN`/`ADJUDICATE` in `epic-run.mjs`, the same names in `fix-run.mjs`) are written in the CLI's **aliases** — `sonnet`, `fable` — and the installed binary resolves an alias from a catalog bundled inside it. `fable` meant `claude-fable-5` up to CLI 2.1.256 and `claude-fable-5-1` from 2.1.257. The aliases exist so a CLI update moves every tier forward without editing a table; a CLI that never updates quietly turns them into pins.

- **Idle is the whole contract.** A running process keeps its binary through the swap, but every phase of a run is a *fresh* `claude` process, so an update under a live run hands its later phases a different CLI than its earlier ones got. Idle is asked of `launch.sh --check-idle` — the same `running_count` that enforces `MAX_PARALLEL_EPICS` — so "busy" cannot mean two different things; a dead pane at a shell prompt is idle, as it is for the cap.
- **It holds dispatch's lock across check and install**, so a tick cannot launch into the window between "idle" and "installed". A manual `./remote-control.sh start` doesn't take that lock; the window is one download long and the cost is one run on mixed CLI versions, accepted rather than guarded. While it holds the lock a dispatch tick logs "previous tick still running — skipping": that is the updater, not a stuck tick.
- **`latest`, not `stable`**, decided 2026-09-02: the pipeline's gates fail a broken phase loudly, whereas a stale model degrades output silently.
- **A busy hour is skipped**, not queued — the queue drains to empty often enough to catch up, and the log shows each skip with the count.
- **Exit 0 whenever the host was left consistent** (updated, current, busy, lock held), 1 when the update itself failed. `-n` probes and reports without installing, and is the safe way to check a live host.

## provision.sh (host rebuild)

`bin/provision.sh` rebuilds the box from bare Ubuntu, and runs **ON the host** — never over ssh from the laptop. Bootstrap (the only hand-typed part) is `apt-get install -y git gh` → `gh auth login` → `gh repo clone mikesub/toliki /home/ubuntu/toliki` → `cp etc/repos.conf.template etc/repos.conf` + edit → `bin/provision.sh`.

Covers: system packages (git, tmux, jq, curl, gnupg), node 24 via NodeSource (CI pins 24), gh, docker-ce + buildx from Docker's own repo, a per-repo check that merged branches are auto-deleted (reap's worktree pass reads their absence as proof of delivery — see its section), log rotation for the harness cron logs (`etc/harness-logs.logrotate` → `/etc/logrotate.d/harness-logs`), the supabase CLI (`.deb` from the release page — `npm -g` is explicitly unsupported by Supabase), Claude Code, the Codex CLI, clones of this repo and everything in `REPOS`/`REPO_ORIGINS`, the per-item `~/.claude/{skills,agents}` symlinks (same semantics as `setup.sh`), and `CLAUDE_HARNESS_DIR` merged into `~/.claude/settings.json` with jq. Codex is only installed and authenticated in this stage; the engine registry still contains Claude alone.

- **Idempotent by construction, not by re-doing work.** Every step reports what it found and what it changed; a healthy box produces zero changes and exits 0. Versions already present are reported, never upgraded — a provision run must not be able to move node or the CLIs under a fleet of live sessions (the claude binary has its own idle-gated path, `bin/update-claude.sh`).
- **It refuses rather than clobbers.** A real directory where `~/.claude/skills` should be a symlink, an unparseable `settings.json`, a registry path that exists but isn't a checkout — each is reported as a manual step and left alone. A clone parked off `main` warns (launch.sh assumes main) but is never switched.
- **The interactive gates are checked, never attempted**, and each makes the run exit non-zero with the exact command to run: `gh auth status`, `codex login status`, workspace trust per clone (read out of `~/.claude.json` as `projects["<path>"].hasTrustDialogAccepted` — see the trust trap above), and bypass-permissions acceptance (read out of `~/.claude/settings.json` as `skipDangerousModePermissionPrompt` — the silent-deadlock trap above; checked but never set, because accepting it is a consent decision). Claude Code login is a file-presence heuristic (`~/.claude/.credentials.json`), since the only authoritative check would be spending a request. Codex has an authoritative read-only probe, and a miss points to `codex login --device-auth`, the device-code flow for a headless host; its cached credentials are secrets under `~/.codex` and are never read or copied by provisioning.
- **Docker build-cache GC** installs `etc/docker-daemon.json`, written after BuildKit's cache filled a box to 93%. Three traps it encodes, all documented at the step: `builder.gc` is **not** SIGHUP-reloadable (reload reports success and applies nothing — only a full restart loads it); `dockerd --validate` checks JSON structure but **not key names**, so a typo'd key validates clean and is silently dropped; and the age field is `filter: ["unused-for=168h"]`, **not** `keepDuration` (a BuildKit-internal name dockerd accepts and drops, leaving size caps with no age rule). Hence the check is `docker buildx inspect` — the effective rules as BuildKit parsed them — and never "the write returned 0". Seeing `48h`/`1440h` with a ~790MiB rule means the config didn't load. Validation runs against the **source** file before it's copied, so a config that can't parse never reaches `/etc/docker`; an existing different `daemon.json` is diffed and backed up to `.bak` before replacement.
- **That file is a copy, and the copy is the weak point.** `etc/docker-daemon.json` was vendored from a project's **live production config — the source of truth**; ours is a snapshot that drifts silently, and JSON takes no comments, so the file itself cannot say where it came from. A separate *docker GC config provenance* step diffs the two once the upstream repo is on disk and **warns** on any difference, naming the upstream path — a warning, not a blocker, because drift means the two need reconciling, not that the host is unprovisioned (and the installed policy is verified on its own terms by `docker buildx inspect` regardless). It sits after the clones because that's the first point the upstream file exists — the GC step itself has to run early, before gh auth. A dangling pointer (the upstream repo no longer carrying the file) warns too. `GC_UPSTREAM_REPO`/`GC_UPSTREAM_REL` in `etc/repos.conf` are the link — re-point them if the upstream moves; empty (the template's default) skips the check entirely.

## ⚠️ Do not disturb the user's running sessions

The tmux sessions on the host are the user's live, autonomous work. Never `stop`/`restart`/`stop-all` a session, and never `start`/`epic`/bare-`<name>` (which mutate live state) unless the user explicitly asked you to launch or tear down that specific session. Do not run these "just to test."

- **`bin/merge-worker.sh` belongs in this category too, and is the sharper edge** — it squash-merges to `main`, and `main` deploys. Never run it to see what it does (`bin/merge-tick.sh` runs it for every registered repo, so the same rule covers it). Its queue is readable without it: `gh issue list -R <owner/repo> --label ready-to-merge --state open`.
- **`bin/dispatch.sh` on the host is in that same category** — a tick starts real sessions against real issues, and it needs no arguments to do it. `--dry-run` is the read-only form (it queries GitHub and starts nothing), and it's the right way to see what the queue would produce.
- **`bin/reap.sh` without `-n` kills sessions, deletes refs on origin and removes delivered worktrees** — it only ever targets finished ones, but that is the same class of action as `stop`, so it needs the same explicit ask.
- **`bin/update-claude.sh` without `-n` moves the host's claude binary** — self-gated on an idle box, but it changes what every later phase runs, so treat it like running `claude update` on the host by hand.
- **Only `./remote-control.sh ls`, `bin/reap.sh -n`, `bin/update-claude.sh -n`, `bin/resource-report.sh`, and plain read-only `ssh toliki "tmux ..."` queries are safe** to run on your own initiative. To diagnose a session that `ls` reports as **dead**, `ssh toliki 'tmux capture-pane -p -t <session> -S -60'` prints its scrollback (read-only) and usually shows the error `claude` exited with.
- **When testing, keep it hermetic — the real `ssh` must never fire.** The reliable pattern is a stub directory first on `PATH` holding fake `ssh` (plus `tmux`/`git` for launch.sh, `gh`/`flock` for dispatch.sh, and `tmux`/`git`/`gh` for reap.sh) — see the note below on why shell-function stubs are a trap. None of `bin/launch.sh`, `bin/dispatch.sh` or `bin/reap.sh` sshes, so all three can be exercised end-to-end locally that way; point a copied `etc/repos.conf` at throwaway paths so `REPOS` can't resolve to a real clone. Note `flock` is Linux-only, so a macOS run needs it stubbed even though the host has it.
- **The six suites in `tests/` are all safe to run anywhere, the live host included**, and none needs credentials or a network: `merge-autoresolve.test.sh` (the resolver pair, against throwaway repos under `mktemp`), `launch-epic.test.sh` (launch.sh's two shapes and its probes, against stub `tmux`/`node` and a throwaway clone), `reap-worktree.test.sh` (the worktree GC and every guard that keeps one), `update-claude.test.sh` (the updater against stub `claude`/`tmux`/`flock` — every reason it must NOT move the binary, plus the two where it does), `provision-codex.test.sh` (the standalone installer, PATH and device-auth gates against fake binaries and throwaway homes), and `epic-run.test.sh` — the pipelines end to end against a **stub engine**: a fake `claude` on PATH that answers each step from a fixture keyed by a marker in the prompt it was handed, logs its own argv (which is how the model tiering and `--agent` charters get asserted at all), and counts calls per key so a scenario can fail a step's first attempt and pass its second. Every scenario there is a way the pipeline is supposed to REFUSE to ship — a dead review lens, a deferred finding, an off-schema payload — plus the one path where it does. Add a gate, add a scenario.
- Note the trap with function stubs: this machine's shell is **zsh**, where `export -f` does *not* export a function to child processes. So stubbing `ssh()` in zsh and then running `bash remote-control.sh ...` silently uses the **real** `ssh` and hits the live VPS. If you stub with functions at all, define the stub and invoke the script inside a single `bash -c '...'`.
- If you think you may have touched the host, verify before assuming the worst: `ls` shows what's running, and a repo's `.git/FETCH_HEAD` mtime marks the last launch in it (each one does a `git pull`). Check the repo you targeted — or every path in `REPOS`. No pull after your action ⇒ you created nothing.
